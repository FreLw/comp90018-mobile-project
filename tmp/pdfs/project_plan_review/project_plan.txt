Project Overview
1.1
Problem and Motivation
Most navigation apps are designed to get users from one place to another as quickly as possible.
For our project, we wanted to use the University of Melbourne campus in a different way: not
simply as a map, but as part of the interaction itself.
Our idea is a campus treasure-hunting app where users search for fictional relics around selected
university landmarks. Reaching the correct location is only the first step. Depending on the
treasure, the user may also need to stop moving, keep the phone steady, or face a particular
direction before the relic can be found. We also wanted the project to involve interaction between
users rather than making every treasure a single-player task. For this reason, some relics will
be collaborative. Players can join the same team using a team code, communicate through the
in-app chat, and complete different parts of the same challenge.
The main idea is therefore to make movement, orientation, location and teamwork part of the
treasure-hunting process rather than using GPS as the only trigger.
1.2
Proposed Application
Lost Treasures of UniMelb is an exploration game for Android set on the University of Melbourne
campus. Users can view the artefacts available on a map of the campus, choose one to explore,
and then head to the corresponding search area.
While the user is exploring, the app reads various types of data from the phone. Location
services are used to estimate the user’s position and their distance from the target. Accelerometer
readings are used to detect movement and determine whether the phone is being held steadily.
Orientation data is used to estimate the direction in which the device is facing.
Once the user is close enough to a relic, the app switches from normal exploration mode to a
‘relic scanner’ interface. At this stage, the user may be asked to stop, stabilise their phone and
rotate it whilst following the on-screen instructions. The contextual engine uses the processed
sensor data to determine when the required conditions are met. The relic can then be revealed
and added to the user’s collection.
Some treasures are designed as ‘collaborative relics’. A player creates a team and shares the
generated code with other players. Team members can use the chat function to discuss clues

to reach designated areas or satisfy different orientation and stability conditions. Each phone

1.3
Core Features
The MVP will include the following major features:
• Campus Treasure Map: shows Solo and Collaborative Relics around the University of
Melbourne campus.
• Location-Based Exploration: tracks the user’s position, distance from the selected relic
and nearby search area.
• Motion and Stability Detection: identifies movement and whether the phone is steady
enough for scanning.
• Direction Detection: estimates device heading and provides feedback when the user needs
to change direction.
• Relic Scanner: combines sensor feedback during the final search stage.
• Context-Based Unlocking: uses several sensor conditions together before revealing a relic.
• Treasure Collection: stores previously discovered relics.
• Team Code and Team Room: supports creating and joining multiplayer exploration
sessions.
• Team Chat: allows players to share clues and coordinate tasks.
• Collaborative Relics: requires multiple players to complete parts of the same treasure
challenge.
• Cloud Services: stores or synchronises treasure, team, chat and challenge information.
• Notifications: provides relevant treasure and team updates.

System Architecture
2.1
Module Architecture
The application is divided into six main areas: motion and stability detection, positioning/GPS,
compass and orientation, contextual engine, user interface, and internet services/notifications/collaboration.
Sensor data is processed primarily on the phone. Each detection module produces information
that can be utilised by the contextual engine without the latter having to process the raw sensor
data directly. This allows the responsibilities of the modules to be separated and facilitates the
independent development of their various parts by group members.
The contextual engine aggregates this data and determines which stage of the exploration the
user is currently at. For collaborative challenges, the phone sends only the necessary information
regarding the players’ progress or readiness to the cloud. The cloud is then responsible for
maintaining consistency in the team’s status across the various devices.
The user interface links these components via the campus map, the relic scanner, treasure
collection, the team room and the chat screens.

2.2
Sensor and Data Flow
The sensor data is first processed locally on the Android device. Accelerometer readings are
converted into movement and stability information, location data is used to determine proximity
to a relic, and orientation detection is used to estimate the direction in which the user is facing.
These processed values are transmitted to the context engine, which uses them to control the
current exploration phase and the scanner’s feedback. In the case of a solo relic, the result can
remain on the local device and directly influence the treasure-unlocking process.
In the case of a collaborative relic, the progress of the players involved is also sent to the cloud.
The team status on the server side combines the progress of the participating players and sends
updates back to their devices once the shared challenge is complete.

4.2.2
Sensors
We are planning to use multiple sensors, including gyroscope, GPS and motion sensor, to support
our landmark-based app. Instead of using each sensor separately, we want to combine the data
from different sensors to get a better understanding of user’s location, direction and movement.
GPS will give the user’s real-time location so the app can detect when they arrive at a landmark,
and trigger a cultural pop-up, such as information about unimelb. Gyroscopes will help detect
the direction the user is facing, which can be used to guide the user towards the next landmark.
Motion detection will track user’s movement, which can be used for navigation and for tracking
whether the user completes the exercise.
We won’t simply use one sensor API and read its raw values. Instead, we will combine information
from different sensors to make the result more reliable. For example, different sensors can help
reduce the limitations of using only one sensor. We will also do simple data smoothing to reduce
noise from sensor readings, so the location detection and arrival trigger feel more accurate and
reliable for the user. Also, these three sensors are commonly available on most mobile devices, so
we don’t need extra hardware.
In addition, we play to add a social feature that allows users to connect with other users and
participate in activities together. GPS can also be used to identify nearby users who choose to
make themselves visible, allowing users to discover potential friends in the same area. Friends
can also invite each other to complete landmark-based challenges and compare their progress,
connecting the social feature with existing navigation and exercise features.
4.2.3
Connectivity
Our mobile app will use Internet data and cloud-based databases to support the treasure finding
experience. For the users’ location part, we plan to use Google Maps API to display the map, the
users’ location, and nearby landmarks at the University of Melbourne. The landmarks data will
be stored in an online database to provide description, cultural information and images. When
the users approach a treasured landmark, the app will display the corresponding landmarks’
content.
In addition, we plan to design a social friend-participant system. A user can create a treasure-
hunting session and get a room ID which can be used for sharing with their friends. After a
friend joins the room, the tressure progress will be stored in the cloud database. Two users can
share the same treasure target and cooperate with each other by completing the tasks to get the
treasure.
Every time the users request Google Maps, it will be handled asynchronously in order not to
block users’ interfaces. For error handling, when the network is not stable, we will provide
basic information to the users. Meanwhile, previously loaded landmark information can still be
accessed because it is cached locally in the application.
We believe that this design meets the connectivity requirement because we will apply Google
Maps API in our main functions including displaying the map, showing the location with the
usage of GPS. And the cloud-based database is used for extensibility and scalability.

4.2.4
Responsiveness
Our mobile app will show the users’ location, movement, movement stage, and sensor without
substantial delay. For the sensor usage, the GPS will continuously update the user’s position on
Google Maps, while the motion and accelerometer will show the direction and movement state of
the users. When the user is close to the treasure target, the GPS will quickly give the signal and
update the progress to show the target landmarks’ information.
For the social treasure-hunting room feature, when a friend joins a shared room, they will receive
different tasks for the same target treasure. The app will update the room status and task
progress quickly so that all players can see the latest information. Network requests will run in
the background to keep the interface responsive.
To reduce lag, sensor processing will be lightweight and easy to calculate. When designing the
structure of the app, we should avoid unnecessary UI and request updates, what’s more, Network
request should be handled asynchronously to prevent blocking and heavy delay. To keep the
performance-delay balance, we will set a reasonable hyperparameter for the update frequency
after tests.
To meet the responsiveness requirement, the design can use the sensors to get the user’s location,
movement, and direction and reflect them in the interface with minimal delay.
4.2.5
Technical depth
We want the app to use some algorithms for localization and sensor data. First, we plan to build
a context engine that combines GPS, gyroscope, and accelerometer data using sensor fusion.
This should give us a better idea of the user’s location and movement, instead of relying on GPS
alone.
For localization, we plan to use geofencing algorithm. Each landmark will have a certain radius
on the map, and the app will check the user’s real-time GPS location to see if they entered this
area. When the user reaches a landmark, the app will show a culture pop-up and an exercise
task. We will also look at the motion sensor data when triggering these events. This can help
us check whether the user is actually moving towards the landmark, rather than triggering the
event based only on a GPS update.
We also plan to use location information for our social features. For example, the app can find
other users nearby and allow users to add them as friends. Friends can then interact with each
other and participate in the same landmark or exercise challenges.
Our team believes using several sensors together can give us a more reliable result. We think the
plan is realistic and practical because Android already provides APIs for GPS and the sensors we
need. Geofencing and sensor fusion are also commonly used approaches, so we can use existing
Android functionality instead of having to adding other hardware. We will also keep the different
parts of the app relatively modular, so team members can work on them separately and it should
be easier to manage the development.

4.3.2
Guidelines
We will design the Android interaction guidelines by combining the characteristics of traditional
mobile games and functional apps, and consider the design from 2 aspects: user habits and
ergonomics.
In terms of user habits, we will use the Android bottom navigation bar and
back navigation behaviours that Android users are familiar with. We will also provide visual
feedback for states such as errors and success in ways that are consistent with Android conventions.
Components will generally follow common Android design patterns, while more playful interactions
will be added to special interfaces, such as treasure-related pages. In terms of ergonomics, we
will ensure that buttons have sufficiently large touch targets for easy interaction. We will also
maintain reasonable spacing, alignment, and visual hierarchy to make information easier to
understand.
4.3.3
Flow
For solo mode, after completing the required location and sensor conditions, the user will enter
the treasure reveal page. The user will see the treasure and can view its historical prototype
photograph and related story. The user can return to the map and continue exploring. For
team mode, users can join an existing team using a team code or create their own team. Shared
tasks within the team should be clearly presented, while the style and process should remain
consistent with the solo mode. In addition, users can use public chat rooms easily.
4.3.4
Language
We aim to ensure that all textual and visual information presented through buttons and labels is
concise, clear, and easy to understand. For pop-up messages and instructional labels, we will
use short and commonly understood expressions. Complex technical concepts will be translated
into language that fits the game context. For game-related interfaces, the language will remain
consistent with the overall narrative setting, while still providing users with clear instructions
on how to play correctly. Prompt messages and state labels will also correspond closely to the
current state of both the user and the device.
4.3.5
Reactiveness
The interface will continuously reflect changes in internal sensors, the external environment,
and user information. For internal sensors, the main information, including the user’s location
(GPS), movement status (accelerometer), device stability (context engine), and facing direction
(orientation sensor), will be updated in real time while users are hunting for treasures. The
interface will also provide users with prompts. For external data, the interface will be updated
when the user’s status changes, including task completion, permission updates, etc. If an error
occurs, the interface should also display a notification.
4.4
Innovation
4.4.1
Innovation Overview
Our project’s innovation lies in turning the University of Melbourne campus into an interactive
treasure-hunt environment rather than building a conventional map, quiz, or event information
app. Lost Treasures of UniMelb connects real campus locations with fictional digital relics,

historical references, clues, and organizer-designed tasks. Motion, direction, and location sensing
support the interaction by making relic discovery depend on the user’s real-world context, while
team codes and chat allow users to complete collaborative relic hunts together.
4.4.2
Novelty
The app provides a novel campus exploration model by combining location-based treasure hunting,
historical storytelling, multi-sensor interaction, and team-based event participation. Unlike a
normal campus map or check-in app, users do not simply reach a location and receive static
information. Instead, selected campus landmarks become interactive checkpoints where users
follow clues, satisfy physical-context conditions, and unlock stylized digital relics connected to
university history.
4.4.3
Surprise
The app is a surprising extension of existing campus and event apps because it changes how
users experience familiar university spaces. Ordinary places such as lawns, libraries, museums,
or historical buildings can become part of a game route. The user may need to face a certain
direction, hold the phone steady, or complete a scanner-style interaction before a relic is revealed.
Collaborative relics add another unexpected layer by requiring teammates to coordinate across
locations or conditions.
4.4.4
Tech Knowledge
The project demonstrates technical knowledge by integrating mobile sensing, contextual state
detection, cloud-based content, and responsive UI behaviors. Location sensing detects proximity
to checkpoints; direction sensing supports orientation-aware clues, and motion or stability sensing
helps verify scanner interactions. These signals are interpreted by a Context Engine that decides
whether the user is navigating, searching, scanning, or ready to unlock a relic. For team hunts,
the cloud synchronizes team membership, chat messages, player readiness states, and shared
completion events.
4.4.5
Cross-Disciplinary
The project combines mobile computing with game design, HCI, campus navigation, public
history, education, and event management. Game design contributes to clues, progression,
discovery, collection, and rewards. HCI helps make sensor-driven interaction understandable
while users move through a real environment. Public history and education are reflected in the
use of campus stories and historical references, while event management is supported through
reusable organizer-designed routes and tasks.
4.4.6
Impact
The app can improve campus activities by making exploration more engaging, structured, and
memorable. For new students, it can reduce the uncertainty of navigating an unfamiliar campus
and turn orientation into an active discovery experience. For visitors and current students, it
can reveal historical or cultural details that are easy to miss. For event organizers, it provides
a flexible tool for guiding participants, encouraging attendance, and creating interactive group
activities across campus.
